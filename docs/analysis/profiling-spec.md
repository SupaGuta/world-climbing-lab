# Data profiling — specification

> **Status:** spec for the Layer 1 (analysis) data-profiling step — the first module of `wcl_analytics`.
> **Output artifact:** [`data-profile.md`](./data-profile.md), generated by a reproducible script.
> **Scope:** purely descriptive inventory of the warehouse views. No interpretation, no cleaning, no modelling — those come later and are tracked separately.

## Goal

Produce a single, re-generable markdown report that describes the shape, types,
completeness, and internal consistency of every exported warehouse view. This
report is the factual basis for planning the EDA and cleaning phases.

The profiling must be done by **committed package code**, not by hand, so it can
be re-run as the warehouse grows.

## Package structure

Profiling is the first module of the `wcl_analytics` package. Layout follows the
same philosophy as `wcl_data`: cross-cutting single-file concerns live at the
package root, named by responsibility (no `helpers/` / `utils/` junk-drawer).

```
src/wcl_analytics/
├── __init__.py
├── loaders.py        # load a view (CSV/SQLite) read-only → DataFrame; shared by future modules
└── profiling.py      # compute the summaries + render the markdown report
```

- `loaders.py` owns reading a view into a DataFrame (read-only). Split out from
  the start because every future analytics module will reuse it.
- `profiling.py` owns the profiling logic and the markdown rendering.
- Promote `profiling.py` to a `profiling/` sub-package only once it outgrows a
  single file (e.g. `summaries.py` / `consistency.py` / `report.py`), exposing
  the public API via `__init__.py` so imports don't break.

**Triggering (interim):** a throwaway `scripts/` runner (or a
`if __name__ == "__main__"` block in `profiling.py`) is fine for now. Factor a
real CLI (`python -m wcl_analytics …`, mirroring `wcl_data`) only once there are
a few analytics modules to share it.

## Constraints

- **Read-only.** Read the exported CSVs in `data/exports/` or query the SQLite
  warehouse directly, but never edit `data/wcl.sqlite` (owned by the ingestion layer).
- **`ascents` is large** (~900k rows / ~200 MB CSV): read in chunks or sample it.
  Never load the whole thing into memory.
- **No bulky raw data in the report.** At most a `head(10)` per view, for illustration.
- The report is **descriptive only** — no analysis or recommendations.
- Commit **both** the package code (`loaders.py`, `profiling.py`) and the
  generated report.

## Views to profile

`seasons`, `leagues`, `events`, `competitions`, `athletes`, `cup_rankings`,
`results`, `round_results`, and a **sample** of `ascents`.

## Per-view content

For every view, the report must include:

- **Shape** — rows × columns.
- **Per-column summary** — dtype, % non-null, number of unique values.
- **`describe(include="all")`** output.
- **Categorical columns** (low cardinality, < ~30 distinct): top 15 `value_counts`.
- **Date columns:** min and max.
- **Duplicates:** count of fully-duplicated rows, plus duplicates on the view's
  natural key.

## Climbing-specific extras

- **Disciplines / categories / genders:** distinct values and counts of
  `discipline`, `category`, `gender`.
- **`athletes` completeness:** fill rate of `height`, `arm_span`, `birthday`,
  `country_iso3`, and the paraclimbing / speed-PB fields.
- **`ascents` score columns:** for each discipline, which score columns are
  populated (`top`, `plus`, `time_ms`, `zone`, `points`) — quantify the fill
  rate per discipline.

## Cross-view consistency

- **Join cardinality:** number of `results` per athlete and per competition;
  number of `round_results` per competition.
- **Orphan checks:** rows in `results` / `round_results` / `ascents` with no
  matching `athlete` or `competition`.

## Report layout

- One section per view.
- A short opening section with the generation timestamp and the data source
  (export directory or warehouse path) used.
- Clear, scannable formatting — this is a reference document, read repeatedly.
